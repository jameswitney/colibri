## 4. Parity verdicts

- **Tiny gate: GREEN** (3/3 legs token-exact, both runs).
- **CPU channel: GREEN everywhere** — deploy+pinned `fork_cpu` token-exact on both prompts,
  both runs. R2's independent leg-A records are **byte-identical** to R1's banked fixtures
  (all four sha256-equal; deploy and pinned fixtures also byte-identical to each other — the
  record path is invariant across the history knobs).
- **Greedy channel: byte-identical on every leg of both runs** (9/9 short, 24/24 long —
  CPU and GPU-env legs alike).
- **Pinned HARD gate: RED — the GPU-env leg (`COLI_VULKAN=1`) vs the token-exact TF bar**:
  short 17/18, long 887/900 (deploy) and 891/900 (pinned). Harness exit 1 both runs. Root
  cause, from the leg's own log: **the port's oracle path arms the real Vulkan stack** —
  `dense chain on`, tier on (469 experts, 7.85 GiB), "device 1144 of 9030 routed experts
  (12.7%)" — unlike the fork, whose oracle leg was CPU-bound by construction
  (`target_batch(NULL,…)`; golden-parity-cost.md §3). The port has no cell-hash A/B, so this
  leg is the only GPU-exercising parity leg it has. The divergence is the documented F8
  near-tie/reassociation class (flips at logit ≈ 27–28; e.g. pos 7 → 671 deploy / 2107
  pinned — different tokens per config, deterministic per config).

**Flip stability (the manager's requested characterization):** within a config the GPU TF
flips are fully deterministic — R1 vs R2 flip sets AND values (pos+expected+got) are
identical: deploy {10,12,17,18,21,64,68,103,109,116,121,138,153} (13), pinned
{17,18,40,61,68,87,94,121,153} (9); across configs the sets differ (intersection
{17,18,68,121,153}). The CPU `expected` values are identical at every common position
(fixtures byte-identical), i.e. the instability is the GPU leg's, not the oracle's.

## 6. Findings & quirks recorded (not debugged, per lane scope)

1. The port's oracle path arms the Vulkan stack (above) — the fork's split-contract premise
   ("oracle leg is CPU-bound") does not carry over; worth a line in the eventual harness
   upstreaming note.
2. Fork harness quirks, left unchanged: the header documents `GOLDEN_UPSTREAM_REF` as an env
   override but only `--upstream-ref=REF` parses (and only the `=` form — the two-token form
   hits the unknown-flag branch); the deploy-pass A-vs-A self-stability probe is dead code
   (`real_pass` returns the *pinned* failure flag, so `deploy_rc` stays 0).
3. The harness overwrites per-prompt leg files (`deploy.fork_gpu.out/err`) with the last
   prompt's run — short-prompt evidence survives only in console.log/live capture.
4. `.coli_mfu` in the model dir is mutated by GPU-env legs and unknown to the harness (fork
   predates it); snapshotted/restored manually per the rig's own convention.
