## 1. The one rule (and the filter it had to drop)

```c
    const int next = layer + 1;
    if (next >= T.main_layers) return 0;
    const int cold = !T.pred || !T.pred_ok[next];   /* no big step behind the next layer yet */
    if (cold && !T.ring_cold) return 0;             /* the landed pred-gated cold branch */
    ...
    int nc = st_prefetch_plan(next, S, cand, T.st_per, cold);
```

`st_prefetch_plan` gains a `whole` flag: the cold branch calls it with `whole = cold`, which drops
the **below-rule filter** (`est[e] < R`) and takes every **non-resident** expert of the next layer,
still ranked by the same estimate (the heat, where no prediction exists). The filter had to go, and
the measurement is why: with it, the plan is *empty again* at the model's own short-chunk shapes.
On the smoke (one chunk, S = 72, R = 16, E = 256) the heat-scaled estimate is `heat · S · K / Σheat`
≈ 3 rows for the hottest expert of a layer — nothing clears R, and an instrumented leg showed
`nc = 0`, `the ring 0 jobs`. Coverage by construction means the fork's literal: the whole
non-resident set, and the cap — `st_per`, the half — does the pruning, exactly as the fork's
256-expert read is bounded by its own ring. Everything else is unchanged: the resident exclusion,
the in-RAM skip, the half-alternating slots, the take/join, the inline fallback for every miss, the
SYNC drain, the teardown cancel. Where a prediction exists the plan is the prediction's — the
pred-gated branch's behaviour is bit-for-bit what it was.

Default off is the same one gate: `ring_cold` is read once beside `ring_on` (and needs it), the boot
line adds `its cold layers whole-layer` only when armed.

## 2. The bug the cold arm exposed: the ring's stage pool never freed (PW-B's, now fixed)

The engagement leg that first ran the cold rule filled **one job** and then nothing — the cold plans
were right (42 × 32 candidates) but the reader returned 8 experts once and 0 forever after.
Instrumented (`v4_vkt_ring_batch`'s take loop): `[ringdbg] reader layer N i 0: the stage pool is
full` on every job after the first. The cause is in the **shared release hook**:

```c
static void v4_vkt_unhold(void *ctx, void *h) {
    ...
    if (hold->stage >= 0) v4_vkt_stage_busy[hold->stage] = 0;   /* the ENGINE pool's array */
```

`v4_vkt_ring_batch` hands out holds whose `stage` indexes the **ring's** pool
(`v4_vkt_ring_stage_busy`, a second 8 × 16 MiB pool that exists precisely so the two threads never
share a busy flag) — so every ring fill's release cleared an *engine* stage's flag and left the
ring's busy forever. Two consequences: the ring's fills are capped at the pool's whole capacity
(8 experts) **per run** — W2's `the ring 42 jobs (8 experts)` line was this leak **compounding**
the empty-plans diagnosis, not the empty plans alone (both defects were real; §4 re-attributes the
line) — and each such release falsely freed an engine stage a concurrent engine fill could be
reading into.

The fix is the minimal discriminator: `V4VkHold` gains `int ring;`, the ring's reader sets it,
and the release frees the pool the hold came from (`v4_vkt_ring_stage_back`, the ring pool's own
hand-back). Scope extended by the manager mid-lane on exactly this evidence.

## 3. Unit evidence (`test_vk_tier`'s `ring` case, now 10 legs; + the new source case)

```
stream ring:
  inline: 502 assignments streamed, 0 ring reads, 8 inline loads
  cutting: 502 assignments streamed, 12 ring reads, 4 inline loads
  refusing: 502 assignments streamed, 3 ring reads, 7 inline loads
  pipeline: 4 experts one layer ahead, order 2 3 4 5
  coexist: the other layer's step ran beside the parked job, the take finished it
  sync drain: the quiescent point waited out the parked read for the ring
  teardown: cancelled, bounded to the read in flight
  cold default: nothing handed over, 4 inline loads at the cold step          <- the landed rule stands
  cold on: 4 experts one layer ahead, 4 and 5 of them below the rule, 1 inline load at the cold step
  cold with a prediction: 4 experts one layer ahead, the prediction's order 9 2 3 4
```

The cold legs' fixture: layer 0's history outranks layer 1's tail for the warm start's eight
places, so layer 1 keeps 0,1 resident and 2..9 cold; only 2 and 3 have heat above the rule's rows
(4..9 below it, `R = 3` fixed); the routing names 2, 3, 4 round-robin and 9 on every third slot.
So the cold plan — whole — is **2, 3, then the below-rule tail 4, 5** (a heat plan under the rule
would hand only 2, 3: that is the filter-drop's proof), the cap takes four, the step consumes 2,
3, 4 from the ring's slots and leaves 9 to the inline fallback (1 inline load against the
default's 4). The pred leg runs the same fixture with a step behind layer 1 first: the plan is the
prediction's **9, 2, 3, 4** — 9 in, 5 out, the head by rows — and the step loads nothing inline.
Both cold legs' rows `memcmp`-equal the default's: the ring changes timing, never bytes.

The stage pool's release is pinned at source level (`tests/test_v4_vk_ring_pool_source.py`,
4 tests) in the house pattern of `test_v4_moe_batch_lifecycle_source` — the pools are file-static
in `deepseek_v4.c` and the leak is silent on output (the inline fill covers whatever the ring does
not fill), visible only as fill counts at a 43-layer model's scale, which no fixture reaches: the
hold carries its pool, the release frees the pool the hold came from (both directions), the ring
reader marks its holds and the engine's reader does not, and the ring pool's busy flag has no
other hand. Verified both ways: 4/4 on the fixed tree, and the pre-fix two-line busy-clear (a
file-level `cp`, one precise edit, one run) fails exactly the hand-back test.
