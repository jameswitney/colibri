## 2. The P1 arm (ROWS=1): engaged, and the first chunk killed the device

The placement line above, then during the **first 2048-row prompt chunk**, verbatim:

```
radv/amdgpu: The CS has been cancelled because the context is lost. This context is guilty of a hard recovery.
[VK] chain: queue submit failed (-4): the device is lost
[VK] deepseek_v4 chain: the device was lost; the CPU runs this forward again and from here on (the host's state is current: there is nothing to rebuild)
[VK] tier deepseek_v4: the device stopped answering, the experts stay on the CPU
```

This is **K1's rig boundary (T §3) reached at arm scale**: the armed layer's chunk visit reads its
256 pool-resident experts (3.75 GiB) over PCIe inside one submission — seconds of GPU work in a
frame, exactly the shape K1 measured as the amdgpu hard-recovery trigger and said "the engine
never builds" (true only of window 1's declined arms; the ENGAGED arm builds it). The fallback
then ran the whole model on the CPU with the dense weights read back from disk (385.38 GiB over
the run), which is where the 1043.9 s TTFT and the truncated stream counters (26 of 86 steps,
prefetch 5184) come from. The exit report carries no dmoe line — the chain was lowered at the
loss, so `v4c_report` printed nothing for it; the engagement evidence is the placement line plus
the loss point inside the first chunk's dmoe frame. The log also lacks the rig script's `rc=`/
`vram0=` footer (the caller's own shell timeout killed the wrapper after the scope detached; the
run itself completed — full exit report and generated text present). Per the stop rules the arm
was **recorded, not retried, not debugged**; `COLI_VK_DMOE_ROWS` is a flag (whole chunk), so a
smaller per-frame row cap is a code slice, not a bench improvisation.

## 3. Decisions per the pre-registered rules (L2 spec §7)

1. **Engagement — SATISFIED at decode (P1d, ×3, hybrid); the chunk engagement trips the rig's
   hang detector (P1-r1, §2).** Stage C's premise holds at model scale: the pool opens the
   all-or-nothing gate with zero device residency, exactly as the tiny gate showed.
2. **Prefetch-collapse guard — HOLDS.** C0' 12041 (10013 used) in all 3 reps; P1d 12275 (10267)
   in all 3; against window 1's 12563 (10535): **−4.2 %** and **−2.3 %** — inside the 10 % bar in
   every run. Mechanism, recorded: the funded pool itself moves the count in both directions
   (C0's 272 pool slots hold history experts the stream no longer prefetches; P1d's 256
   pre-queued layer-26 slots displace 256 history warm-start picks — "warm start, 549 experts
   (293 from the history, 256 more to fill the device)" against C0's "549 from the history" —
   and those become cold and prefetchable, +234). P1-r1's 5184 is the device-loss truncation, not
   the `98fcee51` strangling: the device tier held its full 277-expert budget in every run and no
   lever took a device place.
3. **TTFT — no regression beyond the band; the improvement band is untestable on this rig.**
   P1d +1.685 s median vs C0' (+1.1 %), inside C0's own ×3 spread of 5.97 s. The P1 TTFT
   expectation (−2.5–5 s at this 2-chunk shape) belongs to the ROWS arm, which cannot complete
   here (§2); P1d by construction leaves the chunks on the host step.
4. **Decode — inside the no-regression band, no win.** P1d −0.0080 tok/s median (−1.44 %) vs C0';
   D2's ≤ +3 % band holds, and the bands overlap (C0'-r1 0.5514 < P1d-r1 0.5528). Attribution:
   host routed-expert time 144.4/140.3/142.6 s (C0') vs 138.4/140.9/140.5 s (P1d) — the armed
   layer removed up to ~6 s of host step — but device wait rose 20.6–21.5 → 22.7–23.6 s, and the
   tier's own hybrid work collapsed from 475 steps / 511 pool pairs (~1.75 s CPU) to 94 steps /
   94 pairs plus the 2 prompt steps' 61 pairs: layer 26's decode pairs moved from the tier's
   CPU-in-place path to the dmoe 3-frame split — **a shuffle of where the same PCIe-bound work is
   paid, not a removal of it**. One layer of 43 cannot pay while its visit stays bus-bound.
5. **Text — the engaged-arm rule (reassociation class, recorded honestly):** P1d vs C0'
   **diverges, deterministically** — 64 tokens in both, byte-identical within each arm across its
   3 reps, first divergence at char 122, 17 words in ("with each new definition overwriting the
   previous one" vs "with the later definitions overwriting the earlier ones") — mid-generation,
   the rank-order-vs-ascending-id sum class the spec names, not a prompt-step corruption. P1-r1's
   text diverges from sentence 1 (the CPU fallback's numerics — the device chain's
   `GEMM_ROWS=-1` class left with the device; not dmoe evidence). Window-2 C0' also differs from
   window-1 C0's text — the 4 GiB pool changes the tier's serving; cross-config and expected.
6. **No crashes in C0'/P1d; no OOM in any run** (peak 29.9 of 34 GiB).
