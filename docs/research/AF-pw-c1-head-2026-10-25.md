# AF — PW-C1: the head-to-device premise, falsified at unit scale (2026-10-25)

**Date:** 2026-10-25 · **Lane:** PW-C1 (manager-run parity wave, kernel slice 1) ·
**Tree:** `port/up-2276` @ `0c847722` (worktree `pw-c1`, branch `port/pw-c1`; **no code change** — the lane
closes on its own evidence) · **Rig:** the parity rig (RX 6900 XT, RADV), GPU for gate-class runs only: the
tiny oracle legs and a gdb call census; **no benchmark arms**. **Charter:** CAMPAIGN.md's PARITY WAVE
pre-registration — head→device −60…−70 ms/tok against the DPROF/CLI head term's measured 72.9–88.1 ms/tok
(V-g1's legs). **Verdict: PREMISE-FALSIFIED, no code change.** The port already computes the head matmul on
the device at the standing config — the prompt tail and every decode token — through the per-matrix Vulkan
hook, in the fork's own placement. The audits' "port-missing (host path)" premise rests on two host-placement
statements read as compute placement. The pre-registered −60…−70 ms/tok does not exist as a placement win;
manager ruling (2026-10-25): close the lane, corrections ride in §6, the kernel track re-ranks.

## 0. The finding in one paragraph

`head_argmax`'s matmul is not a host op at standing: `head_scores_impl` (`c/deepseek_v4.c:14802`) tries the
device first — `coli_v4_vk_matmul(11, resident, NULL, 0, vocab, d, scores, hidden, 1)` at `:14826`, fmt 11 =
bf16, S=1, O=vocab — and only an OMP host loop on refusal, which never happens at the standing shape (the
guards pass: dense on by default on a discrete GPU, the chain whole so `v4c_partial()` = 0, the head's host
copy kept so `resident != NULL`). The hook was landed in **`9f4eb917` (2026-10-02, "deepseek_v4: resident
fp8 and bf16 matrices on the Vulkan device")** — three weeks before the audits. The fork's device head
(`dsv4_cuda_head_argmax`, `backend_vulkan_dsv4.c:1656`) is the same structure — GPU bf16 matvec, 516 KB score
readback, host argmax with the identical strictly-greater/first-wins tie-break — and the fork's *fused*
`dsv4_cuda_final_argmax` (`:1683`) is an unwired stub returning 0 on the fork too, so there is no further
fork placement to follow. What the audits took for the port's host head is §1's two comments plus the DHO
boot line — all of them statements about *where copies live* or *which engine owns the op in-frame*, not
where the matmul runs.

## 1. Anchors: the port's head path, and the statements the audits misread

- **The call chain at decode:** `target_token` → `final_hidden` (host, mHC mix + rmsnorm — the CPU on both
  trees; the fork's own stub comment says its v1 path "runs final_hidden … on the CPU and calls
  `dsv4_cuda_head_argmax` directly") → `head_argmax` (`:14748`, the `g_v4_prof_head_s` meter — the DPROF/CLI
  head term is *this wrapper's* wall) → `head_argmax_impl` (`:14877`) → `head_scores_impl` (`:14802`):
  resident bf16 branch, VK first (`:14824-14829`), host `head_bf16_dot` OMP loop only on refusal →
  `head_scores_argmax` (`:14864`), the first-maximum-in-vocabulary-order scan over the readback scores.
  Logits/argmax stay host — exactly the fork's split.
- **The hook and its guards:** `v4_vk_matmul_impl` (`:13815`): `fmt == 11` taken; `coli_vk_dense()` —
  default 1 on a discrete GPU (every standing log prints "dense matrices on the device (default)"),
  `v4c_partial()` = 0 at a whole chain ("43 of 43 layers on the device"), `v4_vk_resident` covers the head
  cache (`:13732-13736`), `coli_v4_vk_host_ensure` a no-op while the host copy is kept. Armed at
  `v4_vk_open` `:14644`. First use uploads the device copy once — 1010.0 MiB — and the close line counts it
  (§3).
- **What the audits read instead:** `deepseek_v4_chain.h:41` ("The final streams come back to the host,
  which runs final_hidden and the head as before") — *as before* means through `9f4eb917`'s per-matrix hook;
  the sentence describes the chain's frame boundary, and `:85` ("the head stays on the host") describes the
  **second device's** copies (`COLI_VK_DEV2`'s own table). And the boot line every standing log prints —
  `[VK] deepseek_v4: 489 dense matrices on the device only, …; kept on the host: norms, block scales, the
  router, the indexer's weights_proj, the mHC mixes, the head` (`v4_vk_open`, `:14635`) — is the **DHO
  host-RAM-copy placement line** (`coli_vk_dense_host_placed`): which *host copies* the RAM plan kept beside
  the device copies. The head is in both lists because the plan keeps its host copy resident — which is
  exactly what makes `resident != NULL` at §0.
- **The fork's twin, verbatim:** `dsv4_cuda_head_argmax` (`backend_vulkan_dsv4.c:1656`) — "The GPU computes
  the 129280-row bf16 matvec once; the 516 KB score readback + host argmax is exact"; boot line
  `v4_gpu vk head uploaded rows=129280 cols=4096 (1010.0 MiB; head argmax moves to GPU, CPU reference on any
  failure)` (fork `deepseek_v4.c:16985`; `audit-fork-r1.log:21`). Same size, same placement class, same
  tie-break. The router: the fork computes the gate matvec on the device too, with the **host** top-6
  (`ds4vk_route_top6`, `backend_vulkan_dsv4.c:1092`) — and the port's standing does the same through the
  identical hook (`coli_v4_moe_routed`'s gate call, `deepseek_v4.c:11145`; the top-6 selection is host code
  on both trees).

## 2. Evidence class 1 — the gdb call census at tiny, standing config

Method: the `VK=1` native build at `0c847722`, the tiny fixture, standing defaults (`COLI_VULKAN=1`; the boot
lines match the rig's — chain on, 3/3 layers, dense hook armed), `gdb -batch` with a breakpoint on
`v4_vk_matmul_impl` and a backtrace at every hit. An 8-token prompt / 2-token generation produces **8 hits**:

| hit | caller (frame 2) | what it is |
|---|---|---|
| 1–3 | `coli_v4_moe_routed` | the prompt chunk's gate matvecs (3 layers) |
| 4 | **`head_argmax`** | **the prompt tail's head matmul — on the device** (`<t024>` emitted on return) |
| 5–7 | `moe_token_pipeline` | the decode step's gate matvecs |
| 8 | **`head_argmax`** | **the decode token's head matmul — on the device** |

Every head call, decode included, went through the device hook; no refusal. Corroboration by the engine's
own counter: 8 generated tokens → `32 matmuls on the GPU`, 16 → `64` (slope 4/token = 3 gate calls + 1 head,
the census above), and with the hook disarmed (`COLI_VK_DENSE=0`, the decline path — the chain untouched) the
same runs print **0** — all 32 are the per-matrix hook's, and the tokens are identical either way.

exactly as the fork's boot line uploads it.

## 5. What the 72.9–88.1 ms/tok head term actually is (the residual, recorded)

The DPROF/CLI head term is the wall of `head_argmax`'s wrapper (`g_v4_prof_head_s`), and at model scale that
wall is **not host matmul** — it is the per-op cost of the per-matrix call: the x upload, the submit, the
**fence wait** (which absorbs whatever is queued ahead on the queue at the token's tail — the chain's
deliberately not-waited A2 shared-expert frames, the tier's device expert work, promote copies: the same
interleave V-g1 measured as A2 device 10.6 + tier decode device 9.6–12.5 + promote ≈ 9.7 ms/tok), the generic
bf16 GEMV over 1.06 GB (the census's own class measurement for this shader family: 70–114 GB/s ⇒ ~9–15 ms),
and the 517 KB readback. At tiny the same call is **0.0 ms/tok** (the head is 128×128; the DPROF line reads
0.0 with the device path on at standing — and 0.0 with it forced off, so the term cannot distinguish at tiny;
the gdb census of §2 is what does). Per-leg model-scale values: 72.9 / 88.1 / 81.4 / 48.1 ms/tok (V-g1 a-r1,
a-r2, b-r1, c-r1). A finer decomposition needs an instrumented model-scale run — the manager's rig class, not
this lane's GPU budget. **The fork pays the same class of cost** for its head call (same submit + readback
structure) and prints no head term of its own, so the port-vs-fork delta *inside* this term is unmeasured;
the pre-registered −60…−70 assumed the whole term was recoverable host compute, and it is not.

**Follow-up ledger (PORT-NOVEL, not the fork's placement, outside this wave's mandate):** an in-frame
head/tail fusion — the head GEMV riding the chain's existing per-token tail frame (the 87th frame, today the
streams return) or a fence-bypass readback — would attack the submit/wait half of the term. It has no fork
precedent to follow and needs a fresh pre-registration with a measured baseline before anyone chases it.
